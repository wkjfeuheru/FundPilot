## 1. 评审方法

1. **纵向追溯**：以需求功能点（F-U / F-A / F-D）为起点，逐项核对架构模块、数据库表、API 接口是否闭环；
2. **横向交叉**：需求业务规则（BR/CR/ER）↔ 数据库列与枚举 ↔ API 请求/响应/错误码逐条比对；
3. **脚本辅助核对**：
   - `schema.sql` 建表 41 张，与 03 文档表清单 100% 对应；
   - `schema.sql` 索引 64 个（含唯一键），名称全部在 03 文档出现；
   - 04 文档接口编号去重后 87 个（含 5 个内部工具接口），与清单一致；
   - BR-01~39、CR-01~16、ER-01~17、F-U/F-A/F-D 编号引用无越界、无未定义引用；
4. **规范对照**：逐条对照 `CLAUDE.md` 与 `docs/rules/database-rules.md`，无法满足项按"声明性偏离"登记。

## 4. 架构合理性检查

### 4.1 技术选型

| 项 | 结论 |
|---|---|
| Java 21 + Spring Boot 4.0.9 + WebMVC | 符合 `CLAUDE.md`；同步阻塞模型满足 NFR-P6，SSE 由 WebMVC 原生支持 |
| MyBatis + 手写 XML + 手动分页 | 符合规范；复杂三级组合/客户 360 查询适合 XML 承载 |
| MySQL 8.0 + Redis | 符合；Redis 仅缓存/计数/限流/可选会话，不作业务主数据 |
| React 18 + TS + Vite + Zustand + React Router | 已评审确认（Q1）；样式沿用原型 CSS Token，降低还原风险 |
| Python + FastAPI + LangGraph + DeepSeek | 已评审确认（TODO-05）；AI 独立进程，故障隔离，不直连业务库 |
| Outbox + 调度租约 | 与现有工程实践一致，避免引入 MQ 强依赖 |
| Nginx / RabbitMQ / quant 服务 | 均定位为可选或演进期组件，不阻塞本期 |

**结论**：技术栈未变更，选型依据充分。

### 9.1 确认后的关键实现口径

1. **注册开户**：`POST /api/v1/auth/registrations`（匿名、无 CSRF、无幂等键）；事务创建 `user`；投资者额外创建 `customer`（客户编号自动生成）与 `cash_account`（`app.registration.investor-demo-cash`，默认 50000.00）；不创建 `risk_profile`；不创建会话。
2. **分红**：`fund_dividend` 仅由净值导入写入；交易记录可展示演示分红流水，无创建接口、无调度任务。
3. **调仓结算**：TA 成功时 `cash += 调出确认金额 − 调入确认金额 − 费用`；在途冻结仍为 `max(调入−调出,0) + 费用`。
4. **日期序列化**：`tradeDate`/`navDate`/`validUntil`/`snapshotDate` 等按 `YYYY-MM-DD`；`createdAt`/`pushedAt`/`evaluatedAt` 等按 Instant UTC（`Z`）。
5. **交易日**：`trade_date` 取业务日期；非交易日顺延至下一交易日；TA 按该 T 日净值确认，避免 `TA_NAV_NOT_AVAILABLE`。
6. **行业穿透**：基金层构建返回 `industryConstraintAvailable=false`；单基金/单管理人约束继续计算；不新增行业表。
7. **测评过期**：`USER-01` 无画像返回 404 引导测评；`TRADE-01/03` 仅提示"建议先测评"，不拦截；`CLIENT-04` 与 AI 策略匹配仍要求 KYC 有效。
