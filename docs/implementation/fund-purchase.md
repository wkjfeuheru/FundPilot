# 用户端基金申购实施记录

## 范围与实施方案

依据设计 01 F-U-209/501/505/506、BR-32～39、DF-15，04 TRADE-01/03/05/06/07。

1. 先补真实 MySQL/Redis 接口验收：精确试算、风险门槛、冻结、隔离、幂等重放、并发余额竞争、事务回滚；再实现接口。
2. 申购由 Session 派生用户；金额为两位小数字符串，服务端重算费用、重查风险与可用现金。锁定现金账户后读取待登记冻结合计，订单、明细、审计、幂等记录同事务提交。余额及持仓不变。
3. 使用现有 `trade_order` 自增主键作为平台委托序号（跨日不回退），形成 `T-YYYYMMDD-NNN`（至少三位）。不修改既有 schema。交易日历批量读取，缺行按工作日兜底并告警。
4. 全局幂等键绑定用户、路径及规范化请求摘要；Redis 保存首次 201 响应 7 天，数据库唯一约束为最终防重依据，缓存不可用/丢失时重复请求 409。业务校验失败不占键。
5. 基金卡片与详情入口打开申购表单：异步试算、风险确认、提交、防连点、结果不确定时沿用原键重试。交易页显示资金三项、URL 筛选分页、详情和只读 TA 状态。
6. 完成前后端全量测试、构建、独立代码审查、浏览器桌面/窄屏验收，记录可复现演示路径及实际订单。

本次终点是 `PENDING_TA`，`taReceipt=null`。设计的待登记队列直接来自交易表，不另建 TA 请求或提交 outbox；终态 outbox 属于后续 TA 回执模块。本次不实现赎回、定投、TA 确认和结算。

- 基金超市 → 任意基金“申购”或详情“申购该基金” → 输入金额 → 查看试算和风险提示 → 确认申购 → 查看这笔交易。
- 交易记录 → 查看资金余额/冻结/可用 → 筛选“待登记确认” → 查看委托详情。首笔演示委托为 `T-20261116-001`；继续演示会增加新的冻结金额。
- 若网络结果不确定，沿用原提交凭证重试；浏览器同标签页刷新/关闭重开后保留该凭证。缓存丢失导致无法重放时，先核对交易记录，再明确勾选已核对并结束本次尝试。结束不会撤单；下一次提交是另一笔委托。
- TA 回执写入、T+1 成交结算、持仓更新、终态事件派发由后续 TA 模块完成。本次用户端没有确认成功/失败按钮，也不会自动假成交。

## 实现约定

- 新增 5 个 API：`POST /trade-order-quotes/purchases`、`POST /trade-orders/purchases`、`GET /trade-orders`、`GET /trade-orders/{id}`、`GET /cash-accounts/current`，统一前缀 `/api/v1`。
- 所有资金变动的后续模块须遵守同一现金账户行锁顺序，再计算待登记冻结合计。交易表状态是冻结金额的事实来源，禁止额外维护另一份冻结余额。
- 试算/提交均由服务端读取最新费率、净值、有效风险画像并重算；前端不计算金融金额，金额比较使用整数分（BigInt）。
- 幂等缓存先于事务锁释放写入，重放必须同时匹配已提交数据库记录和响应摘要；回滚遗留缓存不会被信任。平台过期键清理任务尚未实现，当前保留数据库唯一键以继续防重。
- 日历缺行按设计使用工作日兜底并记录日志；本地未补入完整节假日日历。
- 未修改全量 schema，未新增数据库迁移；保留工作区其他风险测评开发改动。
